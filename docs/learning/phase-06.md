# Phase 6 — derivation notes (the API and Part I assembly)

## Why matching OpenAI's request/response shape matters

Plenty of existing tools (client libraries, chat frontends, evaluation
scripts) already know how to talk to OpenAI's API. If Kiln's API answers in
that exact same shape, all of those existing tools work against Kiln
immediately, with nothing more than a different server address -- nobody
has to write a new client just to talk to this particular engine. That's
the entire reason "OpenAI-compatible" is a meaningful design goal on its
own, independent of anything OpenAI-specific about the model behind it.

## Why streaming is just the same loop, revealed one step earlier

The non-streaming endpoint runs the whole generation loop and then hands
back the finished text all at once. The streaming endpoint runs the exact
same loop -- but instead of collecting every word before responding, it
sends each word to the client the instant it's produced. Nothing about the
underlying generation changes; only when the client gets to see each piece
changes. This is why streaming didn't need a second implementation of
generation -- it needed the existing loop's insides exposed one level
higher up, so each step's word could be handed off immediately instead of
appended to a list.

## A real bug this phase caught: raw bytes are not the same thing as text

While wiring the API's streaming endpoint to actually decode tokens back
into text, one generated byte crashed the whole request with a Unicode
error. The cause: our tokenizer is byte-level, so decoding hands back raw
bytes, and a single raw byte on its own isn't always a complete, valid
character -- some real characters are built from more than one byte, and
an untrained model (or even a trained one, mid-character, one word-piece
at a time) can produce a byte that only makes sense once the next byte
arrives too. The fix was to stop assuming every decoded piece is
automatically valid text, and instead decode with a "replace anything
broken with a placeholder character" policy -- the same approach real
byte-level tokenizer serving code uses, not a workaround specific to this
project's toy model.
